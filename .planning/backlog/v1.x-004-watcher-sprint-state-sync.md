# Sprint state.pending_question_ids not synced until AttentionWatcher runs

## Repro

Drop question files directly under `~/.clawteam/teams/<team>/sprints/<id>/questions/`. Run `clawteam sprint status <id> --team <team>`. Output says `pending questions: 0` despite files existing. The sprint's `state.json` also shows `"pending_question_ids": []`.

`clawteam attend` (which walks the filesystem directly) correctly finds the files, so the disconnect is specifically between filesystem reality and sprint state.

## Root cause

`AttentionWatcher` (Plan 07-03) is the component that polls question directories and updates `SprintState.pending_question_ids`. It's designed to run as a background process but has no explicit start/integration point in the normal sprint lifecycle — `sprint start` does not automatically launch the watcher.

## Options

A. Auto-start `AttentionWatcher` on `sprint start` (one watcher per team; tie lifetime to sprint running status).
B. Make `sprint status` itself do a one-shot filesystem reconciliation before printing (cheaper, no daemon).
C. Have `InteractionGate` evaluation call the reconciliation synchronously when it runs.

Option B is the minimum-viable fix — no long-running process, `status` always shows truth.

## Impact

Low in practice because the InteractionGate itself consults the filesystem directly before deciding whether to block or unblock. The sync gap is a **UX lie** (status claims 0 questions when there are questions) but not a correctness gap.

## Files

- `clawteam/attention/watcher.py` — AttentionWatcher implementation (Plan 07-03)
- `clawteam/cli/commands.py::sprint_status` — needs optional reconciliation call
- `clawteam/sprint/state.py::SprintState.pending_question_ids` — the field being out of sync
